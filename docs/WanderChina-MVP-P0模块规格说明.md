# WanderChina MVP P0 模块规格说明

## 1. 范围与优先级

本期 P0 实现“首页/发现、景点攻略、旅游社区、AI 助手”四个模块。行程规划（P1）和实用工具（P2）只展示“Coming soon”占位页，不提供业务逻辑、数据写入或 AI 能力。

| 模块 | 优先级 | 本期目标 |
|---|---|---|
| 首页/发现 | P0 | 让首次访问用户快速发现可信的景点与社区内容。 |
| 景点攻略 | P0 | 提供可执行、可追溯的英文景点信息。 |
| 旅游社区 | P0 | 让游客发布问题、获得回答并沉淀经验。 |
| AI 助手 | P0 | 基于已审核攻略内容回答景点相关问题。 |
| 行程规划 | P1 | 占位页。 |
| 实用工具 | P2 | 占位页。 |

---

## 2. 首页/发现

### 2.1 模块边界定义

**In Scope**

1. 展示运营编辑推荐的景点和专题内容。
2. 展示按互动量统计的热门帖子。
3. 展示按浏览量统计的热门景点。
4. 提供城市筛选入口，并跳转到对应景点或帖子详情。

**Out of Scope**

- 不做基于用户画像、行为或位置的个性化推荐算法。
- 不做无限滚动信息流、实时热榜或推送通知。
- 不做广告位、商业内容投放和 A/B 实验平台。
- 不做全文搜索，搜索能力留待后续版本。

### 2.2 核心用户故事

1. As a 首次来华游客, I want to 查看编辑推荐的城市景点, so that 我能快速找到可靠的旅行起点。
2. As a 正在规划行程的游客, I want to 按城市浏览热门景点和帖子, so that 我能了解其他游客正在关注的问题。
3. As a 运营人员, I want to 配置首页推荐内容及排序, so that 我能优先展示已验证且时效性高的信息。

### 2.3 验收标准

| 核心功能 | 验收标准 |
|---|---|
| 编辑推荐展示 | WHEN 用户进入首页 THEN 系统展示已发布的编辑推荐景点与专题 AND 按运营配置的排序返回。 |
| 热门帖子展示 | WHEN 用户进入首页 THEN 系统展示已发布的热门帖子 AND 不展示已删除或审核未通过的帖子。 |
| 热门景点展示 | WHEN 用户进入首页 THEN 系统展示热门景点卡片 THEN 卡片包含名称、城市、封面和简短说明 AND 仅统计已发布景点。 |
| 城市筛选 | WHEN 用户选择一个城市 THEN 系统仅展示该城市的热门景点和热门帖子 AND 筛选状态在当前页面保留。 |
| 内容跳转 | WHEN 用户点击景点或帖子卡片 THEN 系统进入对应详情页 AND 不存在或已下线的内容返回友好提示页。 |

### 2.4 数据模型概要

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `City` | `id`、`nameEn`、`nameZh`、`status` | 城市主数据，供跨模块标签与筛选使用。 |
| `Attraction` | `id`、`cityId`、`nameEn`、`summary`、`coverImageUrl`、`status`、`viewCount` | 首页热门景点的数据来源。 |
| `Post` | `id`、`authorId`、`cityId`、`title`、`content`、`status`、`likeCount`、`commentCount`、`createdAt` | 首页热门帖子的数据来源。 |
| `EditorialRecommendation` | `id`、`contentType`、`contentId`、`title`、`sortOrder`、`publishedAt`、`status` | 运营配置的首页推荐项；`contentType` 为景点或专题。 |

关系：一个 `City` 包含多个 `Attraction` 与 `Post`；一个 `EditorialRecommendation` 指向一个已发布内容；`Attraction` 和 `Post` 的互动或浏览字段用于生成热门内容。

### 2.5 模块间依赖关系

- 依赖景点攻略模块提供已发布的 `Attraction`、浏览量和封面信息。
- 依赖旅游社区模块提供已发布的 `Post` 及点赞、评论数据。
- 数据流向：首页只读取并聚合景点、帖子和推荐配置；用户点击后分别进入攻略详情或帖子详情。

## 3. 景点攻略

### 3.1 模块边界定义

**In Scope**

1. 按城市浏览已发布的景点列表。
2. 展示景点详情，包括介绍、开放时间、地址和交通信息。
3. 展示“参观前须知”，包括预约、证件和入口要求。
4. 展示按步骤编写的到访指引与信息更新时间。
5. 记录景点详情浏览量，为首页热门景点提供数据。

**Out of Scope**

- 不做门票购买、库存查询、预约代办或支付。
- 不做地图导航、实时交通、打车或外部地图 API 集成。
- 不做用户攻略编辑、评分体系或图片社区。
- 不做非景点类目的完整商家黄页。

### 3.2 核心用户故事

1. As a 英语游客, I want to 查看景点的预约与证件要求, so that 我不会到现场后才发现无法入场。
2. As a 首次来华游客, I want to 阅读分步骤的到访指引, so that 我能知道从出发到入园的下一步动作。
3. As a 信息维护人员, I want to 更新并发布攻略信息, so that AI 和游客都使用经过审核的最新内容。

### 3.3 验收标准

| 核心功能 | 验收标准 |
|---|---|
| 城市景点列表 | WHEN 用户进入城市景点页 THEN 系统展示该城市已发布景点 AND 每项包含英文名称、封面、摘要。 |
| 景点详情 | WHEN 用户打开景点详情 THEN 系统展示介绍、地址、开放时间和交通信息 AND 显示信息最后更新时间。 |
| 参观前须知 | WHEN 用户查看景点详情 THEN 系统展示预约、证件、入口要求等已配置须知 AND 未配置字段不编造内容。 |
| 到访指引 | WHEN 用户展开到访指引 THEN 系统按预设顺序展示步骤 AND 每一步可独立阅读。 |
| 浏览量记录 | WHEN 用户成功打开已发布景点详情 THEN 系统为该景点增加一次浏览记录 AND 不因页面刷新重复快速累计。 |

### 3.4 数据模型概要

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `Attraction` | `id`、`cityId`、`nameEn`、`summary`、`addressEn`、`coverImageUrl`、`status`、`viewCount`、`updatedAt` | 景点基础信息。 |
| `AttractionGuide` | `id`、`attractionId`、`introduction`、`openingHours`、`transportInfo`、`bookingRequirement`、`documentRequirement`、`entryRequirement`、`version` | 一个景点当前已发布的攻略正文。 |
| `GuideStep` | `id`、`guideId`、`stepOrder`、`title`、`content` | 到访指引的有序步骤。 |
| `GuideKnowledgeChunk` | `id`、`guideId`、`content`、`embedding`、`status` | 由已发布攻略切分的 RAG 知识片段，仅供 AI 检索。 |

关系：一个 `City` 有多个 `Attraction`；一个 `Attraction` 有一份当前 `AttractionGuide`；一份攻略有多个 `GuideStep` 和多个 `GuideKnowledgeChunk`。只有已发布攻略生成或更新知识片段。

### 3.5 模块间依赖关系

- 向首页/发现提供景点基础数据、状态与浏览量。
- 向 AI 助手提供已发布攻略及其 `GuideKnowledgeChunk`。
- 可从社区帖子跳转至相关景点详情，但社区不依赖景点关联才能发帖。
- 数据流向：运营维护攻略并发布，系统生成知识片段；首页读取景点摘要，AI 检索知识片段，用户阅读行为回写浏览量。

## 4. 旅游社区

### 4.1 模块边界定义

**In Scope**

1. 创建、查看、编辑和删除本人帖子。
2. 为帖子添加一个城市标签。
3. 浏览按发布时间排序的城市帖子列表。
4. 创建、查看、编辑和删除本人评论。
5. 对帖子执行基础内容举报。

**Out of Scope**

- 不做私信、用户关注、粉丝关系或社交动态。
- 不做推荐算法、个性化信息流、话题热榜或推送。
- 不做帖子点赞、收藏、图片上传、短视频发布或富文本编辑器。
- 不做实时聊天室、人工客服工单或内容自动审核。

### 4.2 核心用户故事

1. As a 遇到现场问题的游客, I want to 发布带城市标签的问题帖, so that 熟悉当地的人能理解我的问题并回答。
2. As a 已来过该城市的游客, I want to 回复其他人的帖子, so that 我能分享真实的旅行经验。
3. As a 发帖用户, I want to 编辑或删除自己的错误内容, so that 我能保持信息准确。

### 4.3 验收标准

| 核心功能 | 验收标准 |
|---|---|
| 创建帖子 | WHEN 已登录用户提交标题、正文和城市标签 THEN 系统创建帖子并显示在对应城市列表 AND 标题、正文、城市均为必填。 |
| 浏览帖子 | WHEN 用户进入社区或选择城市 THEN 系统按发布时间倒序展示已发布帖子 AND 不展示已删除帖子。 |
| 编辑与删除帖子 | WHEN 帖子作者编辑或删除自己的帖子 THEN 系统保存更新或将帖子标记为删除 AND 其他用户不能编辑该帖子。 |
| 创建评论 | WHEN 已登录用户提交评论 THEN 系统将评论展示在对应帖子下 AND 评论不能为空。 |
| 编辑与删除评论 | WHEN 评论作者编辑或删除自己的评论 THEN 系统保存更新或将评论标记为删除 AND 被删除评论不再对普通用户显示。 |
| 内容举报 | WHEN 用户举报帖子 THEN 系统记录举报原因和目标内容 AND 被举报内容在审核前仍保持原有状态。 |

### 4.4 数据模型概要

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `User` | `id`、`email`、`displayName`、`role`、`createdAt` | 社区内容的作者；`role` 区分普通用户和管理员。 |
| `Post` | `id`、`authorId`、`cityId`、`title`、`content`、`status`、`createdAt`、`updatedAt` | 社区帖子，`status` 支持已发布与已删除。 |
| `Comment` | `id`、`postId`、`authorId`、`content`、`status`、`createdAt`、`updatedAt` | 帖子下的一级评论。 |
| `ContentReport` | `id`、`reporterId`、`targetType`、`targetId`、`reason`、`status`、`createdAt` | 针对帖子或评论的举报记录。 |

关系：一个 `User` 可创建多个 `Post` 和 `Comment`；一个 `City` 有多个 `Post`；一个 `Post` 有多个 `Comment`；一个帖子或评论可对应多个 `ContentReport`。

### 4.5 模块间依赖关系

- 依赖账户能力识别内容作者和编辑权限；本期账户能力由统一用户实体提供，不单独作为业务模块展开。
- 依赖 `City` 主数据完成城市标签与筛选。
- 向首页/发现提供已发布帖子及其评论数量。
- AI 助手仅可将无法回答的问题引导用户前往发帖页面，**不读取社区帖子作为 RAG 知识源**，以避免未经审核内容影响回答。
- 数据流向：用户创建帖子和评论，社区写入内容数据；首页读取公开帖子；举报记录供管理员处理，不直接改变原内容。

## 5. AI 助手

### 5.1 模块边界定义

**In Scope**

1. 接收用户英文景点或攻略问题。
2. 从已发布景点攻略的知识片段中检索相关内容。
3. 通过 Spring AI 生成基于检索内容的英文回答。
4. 在回答中展示关联景点攻略来源链接。
5. 无足够知识依据时明确告知无法确认，并引导用户查看攻略或前往社区提问。

**Out of Scope**

- 不做通用聊天、情感陪伴、开放世界知识问答或多轮长期记忆。
- 不做外部 API 调用，不查询实时票务、交通、天气、地图、支付或商家数据。
- 不做图片识别、菜单翻译、语音输入输出或人工客服转接。
- 不做自动预约、代替用户填写表单或执行交易。

### 5.2 核心用户故事

1. As a 英语游客, I want to 用自然语言询问景点要求, so that 我能快速获得下一步操作建议。
2. As a 对答案可靠性有要求的游客, I want to 查看 AI 回答所依据的攻略来源, so that 我能自行核对信息。
3. As a 信息不足的游客, I want to 被明确告知 AI 无法确认的内容, so that 我不会依据猜测做出行程决定。

### 5.3 验收标准

| 核心功能 | 验收标准 |
|---|---|
| 提交问题 | WHEN 用户在 AI 助手输入非空英文问题 THEN 系统创建一次问答请求 AND 显示生成中的状态。 |
| RAG 检索回答 | WHEN 系统检索到满足阈值的已发布知识片段 THEN 系统生成仅基于这些片段的英文回答 AND 不使用社区帖子或外部 API 数据。 |
| 来源展示 | WHEN AI 返回有依据的回答 THEN 系统显示至少一个关联攻略来源链接 AND 链接指向已发布的景点详情页。 |
| 无依据处理 | WHEN 检索结果不足以支持回答 THEN 系统明确说明当前无法确认 AND 提供攻略浏览或社区发帖入口。 |
| 问答留痕 | WHEN 系统完成一次问答 THEN 系统记录问题、回答状态、关联知识片段和时间 AND 不将用户问题自动写入攻略内容。 |

### 5.4 数据模型概要

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `GuideKnowledgeChunk` | `id`、`guideId`、`content`、`embedding`、`status` | AI 唯一的业务知识来源。 |
| `ChatSession` | `id`、`userId`、`createdAt`、`updatedAt` | 用户一次短期问答会话；本期只保留当前会话上下文。 |
| `ChatMessage` | `id`、`sessionId`、`role`、`content`、`answerStatus`、`createdAt` | 用户问题和 AI 回答记录。 |
| `AnswerCitation` | `id`、`messageId`、`guideChunkId`、`attractionId` | 将 AI 回答与攻略知识片段、景点来源关联。 |

关系：一个 `User` 可有多个 `ChatSession`；一个会话有多个 `ChatMessage`；一条 AI 回答可有多个 `AnswerCitation`；每条引用关联一个 `GuideKnowledgeChunk` 和其所属景点。

### 5.5 模块间依赖关系

- 强依赖景点攻略模块：仅检索已发布 `GuideKnowledgeChunk`，并链接至 `Attraction` 详情。
- 弱依赖旅游社区模块：当 AI 无法回答时，只提供“去社区提问”的跳转入口，不交换内容数据。
- 不依赖外部服务数据；模型调用通过 Spring AI 完成，但 RAG 业务数据全部来自 MySQL 中的已发布攻略知识片段。
- 数据流向：攻略发布后更新知识片段；AI 检索知识片段并生成回答；问答和引用写入会话记录；用户可从无答案状态跳转至社区发帖。

## 6. 跨模块依赖总览

```text
城市主数据
  ├── 景点攻略 ──> 首页/发现
  │       └──────> AI 助手（已发布攻略知识片段）
  └── 旅游社区 ──> 首页/发现
                  └──> AI 助手无答案时的发帖入口
```

**核心数据原则：** 景点攻略是 AI 的唯一事实来源；社区内容用于游客互助和首页展示，但不进入本期 RAG 检索库。这样可以在社区冷启动和内容审核能力有限的情况下，避免未验证信息被 AI 放大。

## 7. 三周开发约束

1. 第 1 周完成 `City`、`User`、景点攻略数据模型与只读前台页面。
2. 第 2 周完成帖子和评论 CRUD，以及首页聚合展示。
3. 第 3 周完成攻略知识片段生成、Spring AI RAG 问答、来源引用和 P1/P2 占位页。

**上线最小数据要求：** 北京和上海各录入一批已审核景点攻略，并确保每条可被 AI 检索的知识片段都能回链到具体攻略页面。
